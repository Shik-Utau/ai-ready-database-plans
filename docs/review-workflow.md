# 计划书审阅与交接

## 仓库用途

只维护计划、规格和决策摘要。应用代码、原型程序、用户数据、凭据和实验产物留在各自授权的位置。

## 一次讨论如何落地

1. 在飞书或 GitHub 评论中提出问题，附可验证例子。
2. 确认结论和本次范围；新建议、已确认决定和现有实现分开写。
3. 由提案维护者通过分支和 PR 修改 proposal、specs、design、tasks；保持交叉引用一致。
4. 审阅时检查目标、范围、验收场景、证据限制和未决问题，不仅检查措辞。
5. 记录接受或暂缓的结论。首版尚未指定维护者或正式审批人，协作开始时由仓库所有者与参与者约定。

## 与实施衔接

所有会影响行为、职责和验收的阻塞决策处理后，才建立实施交接：目标代码仓库、基准 SHA、选定规格提交、负责人、验收计划及依赖。修改哪个代码仓库需另行授权。

本仓库的 tasks 是后续工作清单，不是执行授权。技术原型通过、文件齐全和规格校验通过均不等于业务获批。不要在本仓库执行应用代码实现。

生产实现完成后，返回实际 PR、测试与未覆盖范围。何时归档及何时同步为主规格，由维护者与审阅者明确记录；不为让状态显示完成而提前归档。

## 避免两份真相

已有 .scratch 工单仍保留在原工作区，本次不迁移其状态。这里只记录截至来源日期的摘要。后续来源结论变化时，以显式文档 PR 核对差异，不假设自动同步。

飞书可维护团队通用说明，本次规格记录采用的章节、版本与结论。不能用持续变化的文档 URL 自动覆盖已审阅规格。

## 共享

本仓库为私人仓库。所有者可在 GitHub 仓库设置中邀请指定协作者；本次创建不自动邀请任何人。协作者先从 README 的提案入口阅读。
